# Define contract reference

**Activation note:** New starts use FrameV2, EvidenceAdmissionV2, and keyed SpecificationDraftV3. The host seals DefinitionTraceV1 before either review. Vera and Carren produce trace-bound ReviewReceiptV2 in that order; host integrity/envelope V2 and the completion predicate replay the latest exact product/trace/support and reports. V1 frames and V1/V2 drafts, admissions, receipts, integrity, and envelopes remain explicit historical readers. New starts cannot silently fall back to an older draft transport or positive admission without the trace.

## Request and composition

`DefineInvocationV2` is the closed caller wrapper around `DefinitionRequestConstraintsV1`, with an explicit `specification_assurance` choice (`reviewed_definition` or `semantic_only`). Legacy V1 constraints map only to `semantic_only`. Create forbids a prior specification and records `not_applicable`; revise requires one. With a prior specification, `semantic_only` checks exact canonical bytes without certifying its producer; `reviewed_definition` verifies its committed, trace-capable Define producer, current review/completion graph and immediate-parent revision closure before consumer run or model creation. Missing/pruned proof, unsupported historical producers, substituted evidence and invalid closure refuse strictly, never retry as semantic-only. Both modes bind a consumer-specific `CompositionAssuranceV1` ref to review/completion; neither certifies full ancestry or ongoing external-source availability. The assurance is not a replacement for SpecificationV1. Single, parallel, chain/resume and supported child-native invocation preserve the same explicit policy; `{previous}` remains the exact core ID.

`DefinitionRequestConstraintsV1` is the closed native request shape: mode; optional requested profile; desired outcomes; audiences; included and excluded scope; hard constraints; non-goals; assumptions; caller- or evidence-owned uncertainties; prior decisions; and standards hints. The host combines the admitted goal with sorted exact input IDs and derives a stable request ID.

Typed ports admit at most one prior `SpecificationV1`, `GroundedSynthesisV1`, `DecisionV2`, and `EvidenceContextV1`. Create mode forbids a prior specification; revise mode requires exactly one. Composition validates exact manifest refs, schema identity/version, artifact kind, registered validator, and canonical bytes.

A prior specification keeps its original `sealing_specification` phase and version. Admission preserves its exact ID in the request, and every revision worker receives it as `prior-specification`. The owning run—not the phase name or highest version across runs—distinguishes imported evidence from the current run's drafts and products. A prior run's higher-version specification must never become this run's latest product. Recovery restores admitted inputs from the exact request artifact's upstream refs.

## Exact source namespace

`DefinitionSourceManifestV1` is host-derived from the admitted request before framing. It binds the complete request ref, request SHA-256, source count (1–128), and an ordered entry for every ordinal with kind, stable source ID, and canonical value SHA-256. The request—not the manifest—contains full values. Framing, Echo when used, authorship/correction, Vera and Carren receive the same exact request and manifest. A restart adopts the exact manifest; it does not reconstruct a new worker-authored inventory.

Coverage diagnostics distinguish missing ordinals and kinds, duplicate ordinals, and out-of-range indexes. Links remain model-authored on items; the host never fills absent rows. Structural completeness does not prove semantic attribution; reviewers compare each source with the request.

## Profiles and readiness

The static registry contains `generic@1`, `software@1`, `business_process@1`, and `research@1`. Every profile is immutable, versioned, digest-bound, and data-only. Profiles require semantic categories but cannot introduce schemas, prompts, code, tools, paths, destinations, or approvals.

Piper framing selects a profile and one route. On new starts the host seals `DefinitionFrameV2` with stable question IDs for request uncertainties and discovered questions (up to 64 active). Caller-owned ambiguity routes to a durable challenge (at most 16 question IDs) and an owner-recorded `DefinitionClarificationResponseV1` with one `answered|declined|not_answered` row per challenged question. A multi-question free-text answer does not resolve every question. Exact answers bind their challenge, request and question IDs; unchanged questions retain support on reframing, changed meaning/owner/materiality gets a new ID. Declined or unavailable answers may lead to a useful blocked product without repeating the same challenge. A narrowly bounded externally resolvable fact or standards question routes to Echo, never to decide caller intent. Historical frames and responses remain V1 readers, not inferred V2 support.

## Draft and canonical product

Rhea normally returns ordinary prose followed by one `SPECIFICATION_CORE:<single-line JSON>` footer and one final SUMMARY. New starts put the closed `SpecificationDraftV3` wrapper in the footer: `{schema_version:3, specification:<keyed semantic core>, support_claims:[...]}`; historical V1/V2 drafts retain their readers. Every semantic row has a bounded draft-local key. Requirements refer to objective keys, acceptance criteria refer to requirement keys, standard support claims refer to standard keys, and supersession replacements use `{kind,draft_key}`. These keys are correction-stable authoring identities; the host still derives canonical SpecificationV1 IDs from semantic content. Only immutable request-source relationships continue to use manifest ordinals. Strict UTF-8 and byte, marker, and trailing-content bounds are enforced. `EvidenceAdmissionV2` inventories exact `caller_response`, `native_evidence`, or `imported_evidence` refs with allowed uses for request uncertainty ordinals, discovered question IDs, or standard categories. A claim names its exact target, status, rationale, and support slot plus locator (JSON pointer or bounded UTF-8 byte range). An admitted slot or category is permission to cite captured bytes, not proof that the claim is true; a contextual EvidenceContextV1 is not automatically support. Standards not marked `satisfied_with_evidence` carry no evidence slots or support selectors.

The semantic validator enforces profile-required requirement and standards categories, exact source coverage, requirement-to-criterion coverage, status-bound standards evidence, disposition consistency, canonical ordering, unique projected stable IDs in all nine semantic collections, deterministic planning handoff, and false planning/taskification/execution flags. Active diagnostics name stable keyed paths such as `/specification/requirements/by-key/<key>/acceptance_coverage`, include bounded statement context where useful, and retain exact source ordinals. Item-side `source_item_indexes` are the sole model-authored source-to-product relation. Rhea emits one disposition/rationale row per request source; the host derives the sealed reciprocal `product_item_ids` index from the item-side links. Compatibility-only draft `product_item_refs` may be accepted from an older pending draft but are ignored. Missing or duplicate rows, unknown draft keys, out-of-range item links, an incorporated source without any item link, or an excluded/unresolved source with an item link remains a semantic failure.

Lineage has two carriers. `SpecificationV1.source_lineage` contains the request and draft artifact IDs, draft digest, imported input IDs, optional prior specification identity, and lineage digest. The exact host frame reference is an `upstream_refs` entry in the specification artifact metadata, not a new field in `source_lineage`. After both reviews, the host integrity and envelope artifacts retain `frame_ref`. New starts also project `DefinitionTraceV1` after the canonical product and before review: it binds that product and keyed V3 draft to the request, manifest, frame, admission, source coverage, selected support refs/locators, protected mappings, and readiness. Trace is deterministic host projection, not independent evidence or approval. A crash between product and trace writes adopts exact bytes before review. A changed product or support graph requires new reviews. Completion independently replays sealing and trace/support checks against the exact frame and latest graph.

A revise draft is a complete replacement. Unchanged semantic items keep their stable IDs. Every changed or removed prior item must appear in explicit supersession; the product also names the prior specification and binds its exact artifact in source lineage.

## Reviews and completion

A new review subject binds the exact request, Piper framing output, host V2 frame and admission, optional Echo evidence, imported products, current complete keyed draft, latest sealed specification, and its product-bound trace. Historical V1 review subjects retain their old shape. Vera PASS produces a host validity receipt. Carren receives the validity evidence; APPROVE produces a dependent quality receipt. Any revision changes the subject and invalidates stale receipts.

Vera's closed third outcome is `UNVERIFIABLE/verification_incomplete/none`, with findings, evidence and specification_delta. It ends durable `incomplete/met:false`, retaining the exact latest product and current review report without evidence, framing, author or critic repair, validity receipt, or positive admission. This is distinct from a verifiable useful blocked specification. Unknown effects alone establish neither a defect nor verification incapability. Both review phases bind `preserve_source_summary_v1`: routing-only repair must preserve the complete source SUMMARY, including confidence and ordered details; absent or invalid original judgment cannot be invented.

Immediately before either review, the host replays native canonical, lineage, selected-ref/byte custody, evidence-admission execution, and existing DefinitionTrace projection/support validators. Only afterward does it append canonical `HOST_MECHANICAL_CHECKS:{schema_version:1,product_ref,source_refs,checks:[...],scope:"host_mechanical_only_not_semantic_or_effect_absence"}` to the signed task. This is inline mechanical evidence, not another artifact store, semantic approval or proof of absent effects. Host-check failure terminalizes incomplete, never author repair. Recovery rechecks the same graph and preserves the exact task; authors never supply post-review integrity/envelope artifacts.

The registration binds `exact_fingerprint_v1`. Before another semantic review repair is charged, the host fingerprints the parsed keyed semantic candidate, support claims and admitted evidence, plus failed structured judgment fields. Report framing, ref/revision identities and specification_delta strategy prose do not count as candidate progress. Exact recurrence for the same review phase yields `incomplete_reason:repair_stalled`, retaining the latest product and reports. Changed candidates may continue through resealing and fresh Vera-before-Carren review under actual operator policy. This is exact comparison, not prose classification or paraphrase detection; no numeric or time cap is introduced.

Completion requires the exact latest product, frame, trace, support bytes, V2 reports/receipts, integrity artifact, envelope, and signed worker execution evidence on new starts. A material unresolved/declined/unsupported question cannot become `ready`; a valid `blocked` specification can complete honestly, while nonblocking questions may remain open in a ready product. Missing, stale, substituted, unrepaired, exhausted, or stalled work cannot complete positively. New starts refuse protected content that cannot fit SpecificationV1 before run/model creation (`DEFINITION_PROTECTED_CONTENT_UNREPRESENTABLE`): preserve hard constraints, non-goals, excluded scope, and binding prior-decision effects exactly rather than truncate or dilute them. An excluded-scope entry has a 2,048-byte product limit; the distinct union of exclusions and non-goals has a 32-item product limit.

Seal corrections follow actual operator policy, with no invented finite allowance when unspecified. Each rejected draft gets its own exact diagnostic before another attempt or honest negative terminal; previous-epoch diagnostics are not current instructions. If a corrective draft repeats the rejected digest or produces the same complete diagnostic set, sealing stalls before spending the next correction. When a complete diagnostic contains only `UNCOVERED_REQUIREMENT`, Rhea may emit one closed `SpecificationDraftRepairV1` bound to the exact base ref, base digest, and diagnostic ref. Its narrow operations may add criteria for diagnosed keys or append diagnosed keys to an otherwise unchanged criterion. The host rejects removals, deleted links, unrelated links, and incomplete issue coverage; verifies custody; applies the operations deterministically; persists a new immutable complete V3 draft revision with the base, repair, and diagnostic in lineage; and sends that result through ordinary full validation. All other defects require a complete replacement draft. The negative terminal's `seal_diagnostics` identifies the final rejected draft and diagnostic, distinct from `repair_diagnostics` and any accepted best partial. A rejected draft is never an accepted specification.

## Consequence boundary

Define produces a specification and planning-input projection only. It does not plan, taskify, approve action, mutate external state, or execute the specification. A `planning_ready` value is a semantic handoff status, not proof that planning or execution began.
