SCA — proposed engine-owned secure code analysis flow

Design target for one durable domain campaign. Penny owns admission, orchestration, exact lineage, budgets, gates, and completion; typed sca-service operators own scanner, index, graph, and isolated-execution mechanics. The campaign derives an evidence-grounded security/threat model after baseline analysis, then composes focused catalog agents, three compatible universal child workflows, same-snapshot generated-rule augmentation, future-release rulepack promotion, and bounded evidence/coverage repair loops.

Proposal, not runtime authority: Penny does not yet support child-skill dispatch from an engine playbook or the sca-service, candidate-rule, and promotion boundaries shown here. Implement those exact-artifact, fail-closed boundaries and a matching TypeScript SCA_FLOW descriptor before registering this package. The campaign's admitted baseline release stays immutable; promotion creates a successor release for future campaigns only.

      Notes

      Threat-model rule: admission freezes only optional caller context/model refs and the modeling policy; it does not require or pretend to possess a completed threat model. Baseline evidence precedes Synthia's versioned operational security/threat model. Full formal modeling uses the same state only when required by policy or a material gap, and repository documents remain target-controlled evidence. Loop rule: a new pass requires a material gap plus a changed input, method, model, or evidence source with expected information gain. Candidate rules require synthetic positive/negative fixtures and fail-closed validation, scan only the same frozen snapshot under finite budgets, and enter the ordinary hypothesis/evidence contract. Promotion requires a verified true-positive generated-rule match and pre-admitted external-rulepack write authority; absent authority or curation failure is recorded without changing finding truth. Coverage closure requires required-family accounting and terminal high-priority hypotheses; final success requires Vera and the host CompletionGate. Operator cards marked SCA SERVICE are closed typed calls from Penny to sca-service, never in-process scanner shells or model access to native query languages, arbitrary mounts, or the Docker socket. Static scanners use pinned one-shot OCI workers, Joern-class state uses campaign-scoped OCI workers, and target-controlled build/test/fuzz execution uses the stronger microVM boundary. Detailed image locks, mounts, cache keys, and provision/doctor/garbage-collection mechanics are intentionally omitted because they are service lifecycle rather than orchestration states. Uniform cancel, malformed-result repair, dispatch-pause/recover, and infrastructure-error seams are omitted for readability and may terminate only in paused, cancelled, incomplete, or typed error states. Child cards represent exact child runs; their internal states remain owned by their own descriptors.
