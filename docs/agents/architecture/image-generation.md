# Image Generation Playbook and Host Adapter

## Status and scope

**Status:** The `imagegen` TypeScript playbook, hidden orchestration skill package, typed admission, deterministic graph preparation, readiness/generation/export host-operation declarations, dual visual review, completion predicate, and constrained host adapters are implemented and provider-free qualified. `imagegen` is production-registered for exact-name skill ingress behind a durable activation authority with closed `disabled`, digest-bound one-shot `canary`, and `enabled` modes. No concrete profile, service port, model asset, source graph, export root, or downstream-project path is compiled into Penny. A qualified deployment injects those private values and its activation policy through the pinned runtime manifest; absence fails closed.

This layer builds on two existing platform boundaries:

- canonical PNG admission and encoding are owned by `png-media.ts`; and
- asynchronous submission, recovery, leases, quarantine, and output custody are owned by the generic host-operation runtime.

Image generation does not create a second engine or give a worker direct network or filesystem authority.

## Authority boundary

The host must inject three private registries before typed start admission:

1. an immutable profile registry;
2. an export-destination registry; and
3. a durable storage-admission owner.

Absence is a refusal. Caller constraints may select a registered profile or destination ID, but they cannot supply an endpoint, graph path, graph body, node class, model asset, export root, overwrite policy, or storage ceiling.

A profile is accepted only when its canonical digest equals the host-approved digest. The registry separately compares every declared node input and execution class with a host-owned class safety policy. Compute nodes use `pure_compute`; exactly the declared output node class uses the narrower `backend_output` authority needed to expose generated bytes through the registered backend output API. Inputs with path, URL, command, dynamic-import, or unrestricted asset semantics are rejected. Concrete profiles remain operator-private inputs.

## Typed start admission

The request contract is closed and bounded. Start admission resolves the exact profile and optional export destination before run creation, validates dimensions against profile policy, computes a worst-case storage requirement, and asks the injected storage owner for a durable reservation. A generated seed is selected once by that reservation when the caller does not provide one.

Only after successful reservation does admission persist the exact:

- `ImagegenRequestV1`;
- `ImagegenProfileSnapshotV1`; and
- storage reservation receipt.

These artifacts are the run's immutable intake evidence. Unknown request keys, unavailable profiles or destinations, profile drift, saturation, and storage estimates above the profile or platform ceiling fail before execution.

The SQLite storage owner reserves transactionally, accounts active reservations at their full ceiling, retains committed bytes after release, and makes reservation, commit, and release calls idempotent by exact identity. Crash recovery may retain unused reservation capacity; it may not overcommit the partition.

## Deterministic graph preparation

The graph builder starts from the exact snapshotted source graph and performs structural mutations at registered node/input addresses. Prompt text remains a JSON value and is never concatenated into executable graph structure. The builder sets:

- positive and negative prompts;
- the deterministic per-slot seed;
- width and height;
- batch size `1`; and
- a deterministic filename prefix.

It removes source metadata by rebuilding closed node objects, validates dimensions and prompt bounds, and persists the submitted graph before creating the operation request. Source and submitted graph digests are distinct evidence.

An optional fallback is allowed only when declared in the approved profile. Its rewrite addresses and replacement values are closed, and the adapter requires the separately approved fallback inventory digest. A fallback cannot introduce a new node class or arbitrary asset.

## Slot ledger

Candidate identity is `(slot, revision)`. Seeds derive from `(base seed, slot)` and remain stable across semantic revisions. The closed ledger admits only:

```text
unattempted → prepared → submitting → submitted → reviewable
                                                   → under_review
                                                   → accepted | critic_failed
critic_failed → prepared (next semantic revision)
```

Operational terminal states include `operational_failed`, `remote_failed`, `remote_unknown`, `downloaded_invalid`, `cancelled`, and `skipped_after_prior_failure`. A remote-unknown state requires a quarantined lease and evidence that the remote work may continue. Review begins only for one complete current image set, increments a review epoch, and requires both critic report refs before acceptance or repair.

## Constrained ComfyUI adapter

The adapter is host-only and registration-bound. It receives exactly the profile snapshot and submitted graph refs named by the operation request through the generic host-operation execution context. It has no artifact discovery surface.

The HTTP client uses direct Node HTTP to one literal registered loopback endpoint. It has:

- fixed routes for readiness, inventory, submit, history, and image fetch;
- no proxy, redirect following, credential, decompression, generic URL, or generic method support;
- request, response, JSON-complexity, image, connect/read inactivity, and bounded poll-interval limits;
- strict response content-type, prompt-ID, history, descriptor, output-node, and one-image checks; and
- no response-body logging or receipt storage.

Before a new submission, the adapter checks readiness and the exact approved inventory digest, node classes, and model identities. It submits one already-built graph with batch size one. The generic operation owner journals the submission guard before the POST and the remote prompt ID immediately after known acceptance.

Queue ownership wait uses the generic owner's finite queue-inactivity interval. Active readiness, generation, download, and persistence use the owner's renewable operation-inactivity lease; the Comfy client reports observed response headers, bytes, and completed responses through that trusted adapter boundary. Socket connect/read timers bound transport silence independently. Backend-fence renewal is ownership maintenance, not operation progress, and cancellation observation retains its separate bounded cleanup grace. Provider-free host-operation tests cover productive renewal, inactivity expiry, and cancellation; the Comfy suite covers cancellation through a stalled response. Neither establishes private-backend behavior.

Only explicit prompt validation rejection proves non-acceptance and permits the bounded pre-acceptance retry policy. Disconnects, redirects, malformed successful responses, and server errors after submission begins are ambiguous and therefore reach generic quarantine. Recovery with a durable prompt ID polls that exact prompt and never posts a duplicate.

A completed history entry must contain exactly one image descriptor under the registered output node. Downloaded bytes are journaled, admitted through the shared PNG decoder, checked for exact dimensions, canonicalized, storage-committed, and persisted through the generic owner under the registered output contract. Invalid media or PNG bytes produce a typed validation and operation receipt but never a generated-image artifact.

## Production playbook

The production registration is artifact-first and keeps deterministic control in TypeScript:

1. host preflight binds the admitted request, profile snapshot, reservation, and slot ledger, then proves backend readiness and the exact primary-or-approved-fallback inventory through a registered asynchronous operation;
2. Annie frames the visual brief only after readiness succeeds;
3. Synthia composes the effective prompt plan, preserving a supplied raw positive prompt byte-for-byte and enforcing a wordless negative policy;
4. the host prepares and invokes one serial generation operation per slot;
5. Vera and Carren visually inspect the complete current image set in parallel;
6. typed repair uses `validation_gap` whenever Vera reports a hard failure and otherwise uses `product_gap` for Carren-only failures; both routes send only failed slots through bounded Synthia prompt adjustment and regeneration with stable per-slot seeds;
7. the host intersects current approvals, uses Carren's total ranking to select the highest eligible candidate, and seals the ledger, selection receipt, manifest, and product envelope; and
8. optional export runs through its own registered asynchronous operation and admitted destination intent before the completion gate admits the exact selected PNG.

The critic phase registration carries `requires_image_input: true`. The generic worker/model-client path resolves positive image-input support from Pi model metadata and rechecks the actual created session model immediately before prompting. Unsupported or identity-drifted critics fail before any model prompt.

Pi loads the package through normal native discovery. Its `disable-model-invocation: true` flag hides it from automatic model advertising while preserving manual `/skill:imagegen` invocation. The same exact package name is bound to the executable production registry, but start admission requires the host runtime manifest and durable activation authority before run creation. Disabled, mismatched, consumed-canary, and replayed starts fail closed. Qualification harnesses exercise the same registration with disposable authority. Hiding is a discovery rule, not a security boundary.

## Export boundary

Export is explicit and separate from generation. The playbook submits an exact complete-set export request to a registered asynchronous adapter; a registered destination supplies the real root and file/byte ceilings. The caller supplies only a bounded destination ID and safe run-directory name. Publication verifies every source artifact digest, creates a new directory without overwrite, writes with no-follow/exclusive semantics, fsyncs files and directories, and returns a typed export receipt. No profile or request contains a host path.

## Operational consequences and diagnostics

A request can consume significant local compute, storage, and time. Generation is serial by design, and a quarantined backend lease can block later work until an operator reconciles the remote job. Provider-free qualification does not prove that a private backend is installed, that a selected critic model is available, that generated pixels are reproducible across backend versions, or that an image is aesthetically good.

Diagnose failures from typed evidence rather than service logs containing content:

- start refusal: inspect profile/export registry resolution and storage-reservation errors;
- pre-submission refusal: inspect profile, inventory, graph-builder, and storage-commit receipts;
- `remote_unknown`: inspect the host-operation disposition and quarantine lease before any manual recovery;
- invalid output: inspect the image-validation and generation-operation receipts; no generated-image artifact is admitted;
- critic exhaustion: inspect the current Vera/Carren report refs and ledger review epoch; and
- completion refusal: inspect the selection receipt, manifest/envelope refs, exact selected-image digest, optional export receipt, and completion-gate failure codes.

## Verification expectations

Hermetic tests cover closed request parsing, profile approval and dangerous-input denial, deterministic seeds and graph mutation, durable reservation saturation/recovery, legal slot transitions and review epochs, exact export, HTTP refusal cases, successful PNG generation, accepted-operation recovery without resubmission, ambiguous-versus-proven submission failure classification, a full real-engine path with fake readiness/generation operations, dual current-image review, raw-prompt fail-closed behavior, registration-owned image capability requirements, activation denial and one-shot consumption, private runtime-manifest custody, and public-source guards. The provider-free claim is limited to engine and contract conformance. Opt-in runners separately verify the private live backend, real multimodal critics, six interruption/recovery boundaries, deployed security posture, and a one-shot production-registry canary before an operator changes the private manifest from `disabled` to `enabled`.
