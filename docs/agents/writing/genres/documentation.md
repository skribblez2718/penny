# Technical Documentation

Write for successful execution. State supported versions, prerequisites, assumptions, paths, identities, permissions, and safety boundaries. Use exact commands and stable component names. Separate normal-user actions from elevated actions.

Make steps produce observable changes. Include expected results, verification commands, failure signals, and recovery actions when evidence supports them. Repeat warnings when the cost of missing them is high. Do not invent flags, configuration keys, paths, output, compatibility, or successful execution.

Use headings, numbered steps, tables, code, and repetition when they improve navigation or precision. Do not vary technical terms for elegance or rewrite code and machine values as prose.
