# SCA host-key installation (v1)

`ScaHostKeyInstallation` is **host-key-authenticated**, not human-authenticated. Owner-only Unix modes (0700 directory, 0600 private key and SQLite ledger) separate Unix users. A process running under the _same UID_ can read the private key or invoke the signing API; a principal string in a signed payload is a bound claim, not proof that that person approved it. Do not present grants as operator-approved without an independently authenticated, isolated signer. Do not give untrusted workers access to the signer or its state path.

A trusted host supplies an absolute, owner-custodied **state directory outside the public project tree**, a stable host-installation ID, the issuer policy/principal and generation, and a trusted clock. State does not appear on normal startup. Call `ScaHostKeyInstallation.provision(directory, hostId)` explicitly once, then `provisionKey()` explicitly to create the first Ed25519 key. Normal operation calls `open(directory, hostId)`; it never repairs missing state or creates a key. Wire the returned instance into `SqliteScaActivationOwner` as `installation_authenticator`, with `installation_authenticator_id` equal to `authenticator.authenticator_id`. Provide the owner's `verifyIssuance` as the SCA-02 host callback. A test-only permissive authenticator is not a production grant source.

After independent host-side validation of qualification, gate, active registration, implementation binding, proposed start, and the requested policy/principal, call `signGrant(grantId, {authority, record, ref, scope})` **explicitly**. This function checks the exact self-seals and ref, signs and durably records the canonical envelope, and returns only grant/key IDs. It does **not** check artifact-store lineage, gate pass, or live host registration on its own, and does not install, register or start a playbook. The caller must supply those checks before invoking this administrative API. Then call `owner.install({authority, record, ref})`. No CLI or production start/registry mutation is installed by this module.

The envelope is canonical UTF-8 JSON: `{"payload":...,"signature":...}` with a closed v1 payload containing the domain `penny.sca-activation.host-key-installation.v1`, host installation ID, signing key ID, grant ID, policy ID, principal ID, generation, issued/not-before/expiry times and the complete authority, issuance record, canonical issuance ref, and scope. The signature is Ed25519 `sign(null, Buffer.from(canonicalJson(payload), 'utf8'), privateKey)`, base64-encoded with padding. Public keys are pinned SPKI DER; the key ID is `key_` plus SHA-256 of UTF-8 `penny.sca-host-key.ed25519.spki.v1` followed by NUL and the DER bytes. Parsing rejects duplicate/unknown members, noncanonical or invalid UTF-8, oversized envelopes and noncanonical signature encoding. The verifier requires exact operand equality, a matching durable grant, a pinned non-revoked key, a valid signature, and current time in `[not_before, expires_at)` with issuance not in the future. The owner rechecks under the ledger's SQLite `BEGIN IMMEDIATE` lock at install, verifyIssuance, and inside consume's write transaction; grant and key revocation use that same lock.

`revokeGrant(id)` immediately invalidates the grant. `revokeKey(id)` invalidates every grant signed by that key. `provisionKey()` is an explicit rotation: it makes the previous key verify-only and uses the new key for new grants; old grants remain valid until expiry or revocation. Never reuse a revoked key. If the private key is lost, new signing fails; existing grants can still verify against the retained public registry. If the ledger or pinned public key is missing or corrupt, verification fails closed. Back up the private key, ledger (including revocation history), host ID, and owner database together under operator custody; validate identity and file modes on restore. A crash between exclusive private-key creation and registry commit can leave an orphan; do **not** silently adopt it or generate a replacement on startup. Inspect and recover such state administratively before retry. This module provides no automated backup, restore, or audit export.

A `VerifiedScaActivationAdmissionViewV1` and a consume receipt do not themselves authorize execution. There is no effectful start path here. Any future start must first rerun SCA-02 against live host state and integrate the resulting view with the owner consume decision immediately before effects; callers must not accept constructed or stale views as an alternate start route.
